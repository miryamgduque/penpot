An AI design agent, built into Penpot

The approaches we took, why they're built into the product, and how it can run: on our servers or the customer's own, including open-source models they host themselves.

What shipped

What's actually built, not a demo

  • Agent panel, native workspace dock: streaming chat, stop, model picker, image attachments, slash commands, live spend meter.
  • Skills & rules, design intent as organizational objects: app → team → file cascade, dashboard CRUD, per-scope enable/disable, promote-to-team.
  • Foundations / DESIGN.md, a short design brief kept with each file, following Google's DESIGN.md convention. A quick interview fills it in, and it's added to every chat with the AI.
  • Enforcement, rules checked at the write path: a raw hex on a token-only file is rejected by the tool, not discouraged by the prompt.
  • Operating modes, graduated governance: suggest for audits, apply-with-review as the default for generative work, auto-fix only for a whitelisted safe set (loss-less token swaps, layer renames).
  • Observers & audit, ambient watchers flag violations as you work; "Fix via chat" hands them to the agent.
  • Durable chats, conversations are saved for each file and come back when you reopen it, along with what each one cost.
Reason 1

Rules are enforced by the software, not just asked for

Other AI tools put your rules in the prompt and hope the model obeys. We put them at the point where a change is saved, so a change that breaks a strict rule cannot be written at all, by any model.

  • The agent edits through the same pipeline a person does, so everything it touches stays undoable, synced to collaborators and exportable, and there is only one way into the file.The agent does not have a private back door into the file. Every change it makes goes through Penpot's normal changes pipeline, so anything it does is undoable, shows up live for collaborators, and exports normally. It works like a real user rather than around the app, and that is what makes the next point possible: with one road in, you can put a gate on it.
  • A change that breaks a strict rule is refused before it lands, with an error naming the fix, so the only way forward is to do it correctly, whichever model is driving.The rules that matter are checked at the tool boundary, the moment a change is applied. Ask for a raw colour on a token-only file and the tool refuses and names the fix ("use a colour token"), so the only way forward is to do it correctly. Because the gate sits below the AI rather than inside its prompt, it holds for any model you bring, frontier, cheap or open-source, and for a human clicking too.
  • The tools report what really happened on the canvas, not what was asked for, because layout moves things afterwards and an agent working from a false picture compounds its mistakes.This matters more than it sounds. Layout often moves a shape after it is placed, so a tool that echoed back the requested position would leave the agent building on a false picture of the screen, and the errors compound. Ours report the settled result instead, list what they find in the order a person reads (top to bottom, left to right) so the agent's mental model matches yours, and verify by reading the file back. When something fails they say so, rather than claim a success that did not happen.
  • Tokens, spacing and naming can be enforced; taste cannot, so judgement calls stay as guidance the agent follows and a human reviews. We claim the narrow thing, and it is the one that causes the cleanup.Anything a computer can test can be enforced: must be a token, spacing on the grid, names following a pattern, no detached components. Judgement calls (is this the right accent colour? is this layout good?) cannot be hard-blocked; those stay as skills and foundations the agent follows and a human reviews. We claim the narrow thing, and it is the thing that actually causes cleanup work.
  • Neither the eleven agents we surveyed nor the design tools designers use do this: their AI generates with your system, but is never bound by it.Three researchers read the actual prompt and config source of eleven open-source agents: only one enforced anything at the tool itself (file restrictions), and none enforced design rules. On the design side, Figma, Motiff, Framer and UXPin all ship AI that can design using your variables and component libraries, and they are good at it. What none of them will do is refuse: a raw colour, a detached component or off-grid spacing is still accepted by the file. Their AI generates with your system; it is never bound by it. Same ingredients, opposite guarantee. They are ahead of us in plenty of other ways; this is the narrow claim we make.
Reason 2

Design intent lives with the file

  • Skills cascade across organization, team, and file. The most specific rule wins, and a strict one can't be loosened lower down, so a rule set once governs every agent conversation in its scope.
  • Foundations travel with the file. The design brief is saved on the file itself (as Penpot plugin data), so copying the file brings it along. No per-machine setup, no prompt files scattered on laptops.
  • Playbooks load only when needed. A short index of what's available rides in the prompt; a cheap model round picks the matching playbook and pulls in its full instructions with the task, instead of carrying them all every time.
  • A file with no direction gets a nudge. Ask for a build on a blank brief and the agent pushes back first: commit to a type, a colour, and a few signature details, rather than produce something generic.

Reason 4

Keeping the running cost down on purpose

To do that, the agent reuses work it has already done, drops old parts of the conversation it no longer needs, and hands the boring parts to a cheaper AI.

  • Prompt caching, stable cached prefix (system + tools), volatile context on the user message; cache hits >90% by round 3.
  • Compaction ladder, stale-result stubbing → structured summary (Task / Done / Decisions / Learned / Open, anchored re-compaction) → hard trim.
  • Side contexts, broad reading delegated to a cheap-model scout; playbook matching, watcher ticks and compaction never bill like design work.
  • Typical screen build today: $1–4 on frontier models; a one-line rename: cents.
The scorecard · 1/2

What building it in gets us

The other way already exists: Penpot's own MCP server, driven from outside by external agents (Claude Code, Cursor, VS Code, Codex).

  • No drift, agent, tools and skills ship with every Penpot release; a refactor breaks at build time, not at a user's desk.
  • Skills are organizational, multi-level, inherited, toggleable per scope. An MCP client just loads skill files, a shared repo at best, with no inheritance, scoping, or enforcement.
  • Reactive skills exist at all: observers need standing presence in the workspace; a protocol client only acts when called.
  • Purpose-built tools beat a blank code box: the agent calls typed, checked actions with plain names (create a shape, change a stroke), so every write passes one gate that rejects off-rule edits. Raw execute_code over the plugin API can do anything, which is exactly why the rules can't be enforced on it.
  • Product integration, caching, spend metering, durable chats, in-canvas forms, wasm renders: none reachable from outside.

Learning from others

What we learned from other open-source AI tools

  • Compaction should keep the lessons, not just recent turns, and anchor a few messages when it re-summarizes (Kimi, opencode).An AI has a limited memory for a conversation, so when a chat gets long it compresses the older part into a summary. The lesson: keep what was actually learned, the decisions made and mistakes not to repeat, not just the most recent messages, and hold on to a few of the original early messages word-for-word so the summary does not drift from what was really said.
  • Staying tightly scoped and asking before assuming beats an over-eager agent (Kimi, Codex).An eager AI tends to do more than you asked: you request one small thing and it redesigns half the file, which you then have to review and pay for. Better to do exactly what was asked and no more, and when the request is unclear, ask a question instead of guessing.
  • Naming the generic moves to avoid, and telling the agent to work in parallel, measurably improves output (bolt.diy; Cline, Zed, Gemini).Two lessons in one. First, instead of telling the AI to "be creative", give it a list of clichés it must NOT do (bland headers, cookie-cutter layouts, placeholder text); a "don't do these" list beats a vague "be original". Second, when several tasks are independent, do them at the same time instead of one by one, which is faster.
  • A passive plan with one step in progress gives visibility without interrupting the user (Codex).For a long task, the agent keeps a visible checklist with exactly one step marked "in progress" at a time, so you can see where it is. It is just there to glance at, it does not stop to ask you to approve each step, so you can follow along without being interrupted.
Infra · today

BYOK through a dumb-pipe proxy

  • User pastes their provider key in Settings → Integrations; keys live server-side only, never reach the browser.Your AI account's secret key is stored on Penpot's server and never sent down to the web page in your browser, so a webpage or extension cannot grab it. You paste it once in Settings, then Integrations. (BYOK means "bring your own key": you use your own AI account and pay that company directly.)
  • The backend proxy (ai_providers.clj) re-emits provider SSE verbatim, no request inspection, no lock-in, provider switching mid-conversation.The go-between server just forwards your request to the AI company and streams the reply straight back, unchanged (SSE is the technique that streams the answer word by word). It does not read, alter, or store what you send, so you are never locked in, and you can even switch AI provider partway through a conversation. (ai_providers.clj is the code file that does this.)
  • Design content goes where you point it: it flows through the proxy to the provider you connected, so that provider is who sees it.Penpot does not run the AI here; your request is passed to whichever AI company you connected, and that company processes your design. The proxy itself keeps nothing, but the panel does save the conversation per file (durable chats), and that saved history includes the design context sent to the AI.
  • Speaks two dialects: Anthropic native, and OpenAI-compatible (OpenAI, Zhipu, Moonshot today), one canonical message model re-encoded per round.Different AI companies expect slightly different request formats. Penpot speaks two: Anthropic's own, and the OpenAI-compatible one that OpenAI, Zhipu and Moonshot all accept. Internally it keeps the conversation in one standard form and translates it for each provider, so adding a new provider is mostly a translation step, not a rebuild.
  • No subscription through Penpot; spend is the user's own, metered live in the panel.Penpot does not sell you an AI subscription. Because you brought your own key, the cost lands on your own AI account, and the panel shows a live running tally of what the current session is costing you.
Infra · the near step

Customers run the AI themselves

  • Penpot is self-hostable; the agent should be too. Any endpoint speaking the OpenAI dialect plugs into the existing proxy: vLLM, TGI, Ollama, llama.cpp servers, pointing at Qwen, Llama, DeepSeek, GLM…You can run an open AI model on your own computers using free serving programs (vLLM, TGI, Ollama, llama.cpp) with open models like Qwen, Llama, DeepSeek or GLM. Because they all can speak the same request format OpenAI uses, and Penpot's pass-through already speaks it, your own model plugs straight in with no new plumbing.
  • The architecture is ready: BYOK = bring your own endpoint is one base-URL field away; the canonical message model already re-encodes per dialect.Today you bring your own key (an account with an AI company). Self-hosting is the same idea but you bring your own endpoint, a web address pointing at your own model instead of a company's. The only missing piece is a text box to type that address; Penpot already keeps the conversation in one standard form and translates it to each provider's format.
  • Data sovereignty, not just privacy: the model runs inside the customer's own perimeter, so their designs and IP never cross into another company's servers or jurisdiction. AI normally turns every design tool into an outbound data flow; self-hosting is what shuts that off.Data sovereignty is about whose laws and whose keys govern your data, not just where it is stored. Most AI features quietly send your design work out to an external company's servers to run the model. When the model runs on your own machines, none of that leaves your network, so you keep full legal and physical control of your design IP.

Watch-outs

  • Most OSS servers lack prompt caching: our cost model leans on it; expect different economics per round.
  • Tool-calling and vision quality vary sharply by model; the 57-tool surface needs an eval gate per model.
  • Our OpenAI-dialect image path is still live-unverified: verify before offering vision on OSS models.

Why it's still right

  • Matches Penpot's open-source identity and enterprise deployments, and its public data-sovereignty stance (aligned with EU tech-sovereignty and GDPR). Our strongest enterprise story.
  • Skills, enforcement, foundations are model-agnostic: the moat is the product layer, not the model.
Infra · a future model

Penpot runs the AI for you

The furthest-out step, not near-term like self-hosting: a future model for once demand and economics prove out.

Pros

  • Zero-setup UX: AI works out of the box; billing bundled with the product.
  • Central model curation, prompt-cache tuning, migration on our schedule.
  • Fleet-level telemetry → evals and regression detection.

Cons

  • We own margins, abuse, quotas and rate limits.
  • The sovereignty cost: design content transits our inference path, so Penpot becomes a data processor and the in-perimeter guarantee from self-hosting is gone.
  • GPU capacity or reseller contracts; on-call for a new class of outage.

A future SaaS tier if demand proves out; BYOK and self-hosting stay the near-term paths.

Beyond the roadmap · furthest out

A detached panel, Claude-Code-style

A longer-term idea: agents that run on their own in the background, with nobody watching, to review and audit a whole team's design files, like automated overnight checks that file what they find.

  • Sessions unbound from an open workspace tab: headless agents against design files.Normally the agent runs inside an open Penpot browser tab. "Headless" means it runs on a server with no window and no person present, working directly on the design files.
  • What it unlocks: standing audit loops, nightly governance / a11y / token sweeps across a team's files, filing findings as comments and reports; long builds that outlive a browser tab; CI for design ("the handoff blocks if the audit fails").Because it does not need a person present, it can run on a schedule: every night it checks a team's files for rule, accessibility (a11y) and token problems and files what it finds.   • The eyes already exist: the agent renders and reviews its own work today, so an unattended one isn't a new capability. The only real question is where it fits: build-with-me stays at the canvas; check-my-work suits detached.The agent already renders images of its work and looks at them to check itself (the visual self-review loop). So a headless version that nobody watches already has the one thing it needs: the ability to see what it is checking. What is left to decide is only where it fits, designing together still wants you at the canvas, while checking, reviewing and batch jobs suit the detached mode.

Roadmap

A realistic path to publishing

Click a milestone for the detail.

Making the prototype solid enough for real users, and it can start now because nothing blocks it. We pull in the cheap, high-value fixes from our survey of eleven open-source agents (mostly better prompt wording). The headline one is parallelism: the agent's worst measured habit was doing independent steps one at a time instead of at once, so we A/B-test two versions of that instruction and keep whichever is faster. We also ship the plan tool (a visible progress checklist), run a live end-to-end check of the OpenAI-compatible and image paths (built but not yet verified), encrypt the stored provider keys (today they are plaintext), add spend limits, and stand up the first automated quality tests.

Real designers use the agent on real work, in organized test sessions. We record everything: the chat with the agent and, crucially, the edits the designer makes right after (every manual fix is honest feedback on what the agent got wrong). A nightly job turns that into concrete improvements to the tools and the agent's instructions, which is the learning flywheel starting to turn. This is the critical path of the whole plan: every later milestone runs on the data the pilot produces, which is why it needs designers' time in scheduled sessions, plus a dedicated server and a model budget.

A separate track that runs at the same time as the pilot, not after it. The main deliverable is small but valuable: a settings field where a customer points the agent at their own self-hosted or open-source model instead of a commercial one. Because open models vary a lot in quality, each has to pass an automated quality gate before we offer it, and we keep a capability matrix recording which models can do what (see images, call tools reliably, and so on). It needs a GPU server so we can actually run those open models to test them. This track is optional: deferring or dropping it does not block the path to publish.

Open the agent to a small set of external teams outside Penpot, to see how it holds up in the wild: real teams, real files, real budgets. The focus is validating the product beyond our own pilot and gathering the quality, stability, and cost data a launch needs. We also use the beta to study the managed-tier question (whether it is worth Penpot hosting the AI for customers), but that is something we learn along the way, not the goal. It depends on what the pilot produced (recorded sessions, designers' edits, and real quality and cost numbers), so it cannot start earlier.

General availability: the agent ships to everyone, but behind a feature flag so we can turn it on gradually and roll it back if needed. Alongside it, we publish clear documentation for enterprises that want to run the whole thing on their own servers with their own self-hosted models. It only ships once the beta has met its exit criteria, the agreed bar for quality, stability, and cost.

What we need to get there

What we're asking for

  • Designers' time, scheduled user-testing sessions; their real work is the training signal.
  • A dedicated server, staging instance with session recording + the nightly agentic analysis loop.
  • Model budget, up to ~$4k/mo covering the pilot, the private beta, and evals across models.
  • optional A GPU server for open-source models, vLLM-class serving to prove the self-hosted story we want to sell.

Why these dates hold

The critical path is the flywheel, not the code: every milestone after August consumes the pilot's results. Fund the server + budget first and the rest is sequencing; without them the dates slip one-for-one.

Nitrate

What an organization governs

  • Mandatory rules. Rules marked mandatory hold everywhere. No team or file can loosen them. The cascade already enforces this; Nitrate is where an org sets it.
  • Allowed providers and models. The org decides which AI providers and models may be used, and whether people bring their own key or use the org's. A compliance boundary, not a preference.
  • Organization-wide foundations. A company tone of voice, naming conventions, and standing context that every team and file inherits, and can tighten but not drop.

What it deliberately does not do

  • Logs cover only the relevant events already defined, nothing an ordinary action wouldn't log. Not a record of who asked the agent what.
  • Whether the agent applies changes directly or only suggests stays each person's choice. The org doesn't override it.
