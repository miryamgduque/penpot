An AI design agent, native to Penpot

The approaches we took, why they bind to the product — and how it deploys: our infra, or the client's, including self-hosted OSS models.

What shipped

The product surface, not a demo

  • Agent panel — native workspace dock: streaming chat, stop, model picker, image attachments, slash commands, live spend meter.
  • Skills & rules — design intent as organizational objects: app → team → file cascade, dashboard CRUD, per-scope enable/disable, promote-to-team.
  • Foundations / DESIGN.md — standing design intent per file, authored by an interview skill, inlined into every conversation.
  • Enforcement — rules checked at the write path: a raw hex on a token-only file is rejected by the tool, not discouraged by the prompt.
  • Observers & audit — ambient watchers flag violations as you work; "Fix via chat" hands them to the agent.
  • Durable chats — per-file conversations in Postgres, restored with their spend meters.
The journey

Three architectures, one survivor

StageShapeWhat it taught us
1 · Plugin appReact app in a plugin iframe driving the public penpot.* API via execute_codeFast to prototype; but capability = whatever generated code does — no validation, no enforcement, bridge tax everywhere.
2 · + MCP doorMCP server exposing the same skills/guard to external agents (Claude Code, Cursor)Protocol clients can't host reactive skills, organizational cascades, or write-path enforcement. Kept as a door, then deliberately retired.
3 · Native agentThe loop, tools, and governance in Penpot's own frontend + a backend streaming proxyTyped tools at the mutation boundary; enforcement, caching, metering, persistence — all first-class product.
Approach 1

Enforcement is structural, not prompt-based

  • Every write rides Penpot's normal changes pipeline — undoable, synced to collaborators, exportable. The agent uses Penpot like a user.
  • Rules that matter are checked at the tool boundary: token-only-colors rejects the call and names the fix. The model cannot route around it.
  • Tools are semantic and honest: reading-order translation, settled-geometry returns, read-back verification — and "I can't" instead of emulation.
  • The eleven-agent OSS survey confirmed: nobody else does this. It is the branch's clearest differentiator.
Approach 2

Design intent lives with the file

  • Skills cascade app → team → file, with mandatory no-loosening — a convention set once governs every agent conversation in its scope.
  • Foundations travel with the file (plugin-data): duplicate a file, the design brief comes along. No per-machine config, no prompt folders on laptops.
  • Playbooks load on demand: a routing index rides the prompt; a cheap classifier round injects the matched playbook with the task itself.
  • A build request on a file with no direction triggers an anti-generic nudge: commit to type, colour, and signature details before building.
Approach 3

Measure, then fix — the postmortem loop

Kahoot session

232 calls, $8.84, wrong flow order baked into the file → tools now speak reading order, validate ids, disclose cascades, return settled geometry.

NYT session

133 rounds for one screen at 1.24 calls/round → composition tools (build_tree, clone_shape, batches), image budgets, playbook injection. Fleet now at ~1.68 calls/round.

Every experiment ran against the live spend meter; more than once the right outcome was refuting our own plan.

Context economy

Costs are engineered, not hoped for

  • Prompt caching — stable cached prefix (system + tools), volatile context on the user message; cache hits >90% by round 3.
  • Compaction ladder — stale-result stubbing → structured summary (Task / Done / Decisions / Learned / Open, anchored re-compaction) → hard trim.
  • Side contexts — broad reading delegated to a cheap-model scout; playbook matching, watcher ticks and compaction never bill like design work.
  • Typical screen build today: $1–4 on frontier models; a one-line rename: cents.
The scorecard · 1/2

Native vs MCP vs Plugin — where native wins

  • No drift — agent, tools and skills ship with every Penpot release; a refactor breaks at build time, not at a user's desk.
  • Skills are organizational — multi-level, inherited, toggleable per scope. An MCP client's skills are files on one laptop.
  • Reactive skills exist at all — observers need standing presence in the workspace; a protocol client only acts when called.
  • A better API than the API — typed, validated, semantic tools with write-path enforcement beat execute_code over a plugin surface.
  • Product integration — caching, spend metering, durable chats, in-canvas forms, wasm renders: none reachable from outside.
The scorecard · 2/2

Where native costs — and the honest answer

Costs

  • Context management is ours to build (compaction, caching, budgets) — Claude Code/Cursor bring their own.
  • Provider dialects, streaming codecs, model catalogs: maintained in-tree.
  • External agents (Claude Code, Cursor, CI) lost their door when MCP retired.

The future door

If external agents matter later: a thin MCP facade over the same native tool registry — same skills, same enforcement, one implementation. Not a second stack.

Infra · today

BYOK through a dumb-pipe proxy

  • User pastes their provider key in Settings → Integrations; keys live server-side only, never reach the browser.
  • The backend proxy (ai_providers.clj) re-emits provider SSE verbatim — no request inspection, no lock-in, provider switching mid-conversation.
  • Speaks two dialects: Anthropic native, and OpenAI-compatible (OpenAI, Zhipu, Moonshot today) — one canonical message model re-encoded per round.
  • No subscription through Penpot; spend is the user's own, metered live in the panel.
Infra · option A

Penpot-managed inference

Pros

  • Zero-setup UX: AI works out of the box; billing bundled with the product.
  • Central model curation, prompt-cache tuning, migration on our schedule.
  • Fleet-level telemetry → evals and regression detection.

Cons

  • We own margins, abuse, quotas and rate limits.
  • Data-processing role changes: design content transits our inference path.
  • GPU capacity or reseller contracts; on-call for a new class of outage.

Fits Penpot SaaS tiers; BYOK stays as the escape hatch it already is.

Infra · option B

Client infra — including self-hosted OSS models

  • Penpot is self-hostable; the agent should be too. Any endpoint speaking the OpenAI dialect plugs into the existing proxy: vLLM, TGI, Ollama, llama.cpp servers — pointing at Qwen, Llama, DeepSeek, GLM…
  • The architecture is ready: BYOK = bring your own endpoint is one base-URL field away; the canonical message model already re-encodes per dialect.
  • On-prem privacy: designs never leave the client's network — the strongest enterprise story we can offer.

Honest caveats

  • Most OSS servers lack prompt caching — our cost model leans on it; expect different economics per round.
  • Tool-calling and vision quality vary sharply by model; the 57-tool surface needs an eval gate per model.
  • Our OpenAI-dialect image path is still live-unverified — verify before offering vision on OSS models.

Why it's still right

  • Matches Penpot's open-source identity and enterprise deployments.
  • Skills, enforcement, foundations are model-agnostic — the moat is the product layer, not the model.
Future · the learning flywheel

The product that learns from its designers

  • Keep learning from the field — the provider/OSS survey becomes a standing loop, not a one-off: two rounds done, adoptions shipped within days; repeat on a cadence.
  • Sessions are data. We already store every agent conversation per file — add the designer's own edits after the agent's work. Every manual fix of a misaligned or mis-nested shape is ground-truth feedback no benchmark can fake.
  • Postmortems on autopilot — a daily agentic loop mines transcripts + edit deltas for insights (what did users undo? re-nest? re-space?), closing the loop back into tools, doctrine and playbooks. Our two hand-made postmortems each paid for themselves; automate the method.
  • Feedback to the user too — the same analysis can surface "the agent keeps getting X wrong in your files — here's a skill/foundation that would fix it."
Future · efficiency & capabilities

Cheaper looks, cheaper minds, richer output

  • Vision economy — we lean heavily on renders, but not every look needs full-res colour. Structure and nesting checks can ride grayscale, downscaled renders (image tokens scale with pixels; payload caps are real). Every KB matters.
  • Multi-model routing — the scout, compaction and playbook matching already run on a cheap model; extend it: an architect/executor split where the frontier model writes the dense spec and a cheap model executes the tool calls — aligned with subtask delegation.
  • Artifacts generation — beyond canvas edits: style guides, handoff specs, component documentation, review reports — deliverables generated from the same file intelligence.
  • Plan generation — a visible plan artifact with one step in progress at a time: passive progress for the user, resumability for the agent (the survey's clearest go signal).
Recommendation

Ship the ladder, keep the moat

  • Default: BYOK (today, done) → custom endpoint field for OSS/self-hosted (small, high enterprise value) → managed tier when demand proves out.
  • Before any OSS-model offer: the eval harness + live verification of the OpenAI-dialect path; per-model capability gating (vision, tool-calling).
  • Keep investing where we're alone: write-path enforcement, organizational skills, self-review — the model market commoditizes; the product binding doesn't.
  • External agents later: thin MCP facade over the native registry, if and when a customer asks.

What we're asking for

  • Designers' time — scheduled user-testing sessions; their real work is the training signal.
  • A dedicated server — staging instance with session recording + the nightly agentic analysis loop.
  • Model budget — a broad set for the pilot and evals (~$2–4k/mo while piloting).
  • Ideally: a GPU server with OSS models — vLLM-class serving to prove the self-hosted story we want to sell.

Why these dates hold

The critical path is the flywheel, not the code: every milestone after August consumes pilot data. Fund the server + budget first and the rest is sequencing; without them the dates slip one-for-one.
